## 이미지를 줄였는데도 홈페이지가 느리다면

**이미지 파일의 용량뿐 아니라, 방문자의 화면에 어떤 파일을 보내고 무엇부터 불러오는지 확인해야 합니다.** 작은 카드에 큰 사진을 보내거나, 글꼴과 분석 도구를 첫 화면의 콘텐츠와 함께 읽고 있다면 이미지를 한 번 압축하는 작업만으로는 해결하기 어렵습니다.

누비오 홈페이지를 점검할 때도 비슷했습니다. 칼럼 이미지는 이미 WebP로 저장돼 있었지만, 성능 보고서에는 여러 썸네일이 ‘이미지 전송 개선’ 대상으로 표시됐습니다. 외부 폰트, 분석 스크립트, 스크롤 효과에 관한 항목도 함께 나타났습니다.

이 글에서는 그 결과를 읽고 수정한 순서를 공유합니다. 소개하는 수치는 **2026년 11월 24일 운영 사이트의 기존 이미지 응답과 로컬 개선본을 비교한 전송량**입니다. 운영 배포 후의 속도나 Lighthouse 점수 개선을 입증한 결과와는 구분합니다. 홈페이지 담당자가 제작사에 무엇을 점검해 달라고 요청하면 좋을지에 초점을 맞췄습니다.

## 1. 보고서의 점수보다 늦어지는 장면부터 찾았습니다

먼저 문제를 세 가지로 나눴습니다. 첫 사진이나 글이 늦게 나타나는지, 메뉴를 눌렀을 때 반응이 늦는지, 읽는 도중 화면이 밀리는지입니다. 같은 ‘느리다’는 말이어도 고쳐야 할 부분이 다르기 때문입니다.

성능 보고서에서 보는 LCP는 첫 화면의 큰 콘텐츠가 표시되는 시점, INP는 클릭·탭 등 상호작용에 대한 반응, CLS는 예상하지 못한 배치 이동을 살피는 지표입니다. 지표 하나를 홈페이지 전체의 사용성으로 해석하기보다 실제 증상과 함께 읽으세요. [Google PageSpeed Insights 안내](https://developers.google.com/speed/docs/insights/v5/about)

직접 점검한다면 [PageSpeed Insights](https://pagespeed.web.dev/)에 메인 주소만 넣고 끝내지 마세요. 방문자가 검색이나 광고로 들어오는 제품 상세, 서비스 소개, 문의 페이지도 확인하고 **URL·측정 날짜·기기 구분·불편한 동작**을 함께 적어 두는 편이 좋습니다.

실제 사용자 데이터와 실험실 결과도 구분해야 합니다. PageSpeed Insights의 실제 사용자 데이터는 최근 28일의 경험을 반영하고, 실험실 결과는 정해진 조건에서 Lighthouse가 진단한 결과입니다. 표본이 부족하면 실제 사용자 데이터가 없거나 출처 전체의 결과가 표시될 수 있습니다. [Google의 데이터 구분 설명](https://developers.google.com/speed/docs/insights/v5/about#real-user-experience-data)

## 2. WebP였지만, 작은 카드에 너무 큰 이미지가 전달됐습니다

이번에 먼저 확인한 것은 원본 폴더의 파일 크기가 아니라 **브라우저가 실제로 받은 이미지**였습니다. 메인 화면의 칼럼 목록은 일정 화면 폭부터 세 열로 배치되는데, 이미지 크기 안내가 그 배치를 제대로 반영하지 못했습니다. 그 결과 작은 카드에도 더 큰 이미지 후보가 선택되고 있었습니다.

예를 들어 화면 폭 1200px, 기기 픽셀 비율 1인 조건에서 칼럼 카드의 이미지 너비는 약 346px였습니다. 기존에는 너비 1200px 이미지가 요청됐고, 수정 후 같은 조건에서는 384px 후보가 선택되는 것을 확인했습니다. 원본 그림을 없애거나 카드 디자인을 작게 바꾸는 대신, **카드의 실제 표시 크기를 정확히 전달하는 부분**을 고쳤습니다.

HTML의 `srcset`과 `sizes`는 브라우저가 화면 조건에 맞는 이미지 후보를 고르는 데 쓰입니다. 같은 화면 너비라도 기기의 픽셀 밀도가 높으면 더 큰 이미지가 필요할 수 있으므로, 표시 너비와 파일 너비가 항상 같아야 하는 것은 아닙니다. [MDN 반응형 이미지 안내](https://developer.mozilla.org/en-US/docs/Web/HTML/Guides/Responsive_images)

비교 조건은 **화면 폭 1200px, 기기 픽셀 비율 1, AVIF를 지원하는 요청 환경**입니다. 해당 썸네일 합계가 약 86.6% 줄었지만, 홈페이지 전체가 그만큼 빨라졌다는 뜻은 아닙니다. 페이지 전체 전송량, 첫 화면 표시 시간, 문의 전환율은 이 수치로 판단할 수 없습니다. 브라우저·기기·캐시 조건이 달라지면 선택되는 이미지와 전송량도 달라집니다.

이미지 검수에서는 파일 크기와 함께 작은 한글, 제품명, 로고도 비교했습니다. 압축률을 높여 파일이 작아져도 방문자가 내용을 읽을 수 없다면 다시 조정해야 합니다. web.dev도 이미지의 바이트 수와 기기에 맞는 크기를 함께 최적화 대상으로 설명합니다. [이미지 성능 안내](https://web.dev/learn/performance/image-performance)

제작사에는 “이미지를 가볍게 해주세요”보다 다음처럼 요청해 보세요.

> 모바일과 PC에서 카드가 실제로 표시되는 너비, 브라우저가 선택한 이미지 크기와 전송량을 함께 확인해 주세요. 고해상도 화면과 세로형 이미지의 잘림까지 고려하고, 제목과 제품 글자가 읽히는지도 비교해 주세요.

## 3. 폰트는 삭제하기 전에 실제 사용 여부부터 확인했습니다

누비오 사이트에는 불러오지만 화면에 적용되지 않는 폰트 스타일시트가 있었습니다. 이 요청은 제거하고, 실제 디자인에 사용하는 외부 글꼴은 유지했습니다. 본문을 먼저 읽을 수 있는 대체 글꼴을 두고, 브랜드용 글꼴이 준비되면 적용하는 방식으로 로딩 순서를 조정했습니다.

웹폰트는 글자 표시를 지연시킬 수 있고, 대체 글꼴에서 바뀔 때 줄바꿈이나 버튼 위치가 달라질 수도 있습니다. `font-display: swap`은 대체 글꼴로 먼저 표시하도록 하는 설정이지만, 글꼴 교체 뒤의 배치까지 자동으로 해결해 주지는 않습니다. [web.dev 폰트 권장사항](https://web.dev/articles/font-best-practices)

그래서 폰트를 바꾼 뒤에는 제목의 줄바꿈, 메뉴 너비, 버튼 높이를 다시 봤습니다. 외부 폰트의 적용 설정이 창 크기를 바꾼 뒤에도 유지되는지도 확인했습니다. 홈페이지에서 쓰는 글꼴·굵기·외부 요청 목록을 정리하면, 디자인을 유지하면서 줄일 수 있는 범위를 판단하기 쉽습니다.

## 4. 분석 도구는 필요한 기록을 남기면서 늦게 불러왔습니다

보고서의 ‘사용하지 않는 자바스크립트’에는 방문 분석과 광고 측정 도구도 포함됐습니다. 이때 표시된 바이트를 모두 삭제 대상으로 볼 수는 없습니다. 초기 측정 구간에서 쓰이지 않은 코드가 이후의 문의나 광고 측정에 필요할 수도 있기 때문입니다.

이번 개선본에서는 기존 분석 도구를 유지하고 외부 파일을 읽는 시점을 뒤로 옮겼습니다. 대신 외부 도구가 준비되기 전에 발생한 이벤트를 임시로 담아둘 수 있도록 처리했습니다. **로딩을 늦추는 작업에는 측정 누락과 중복 여부를 확인하는 작업도 포함돼야 합니다.** 외부 스크립트는 가치가 없는 경우 제거하고, 필요한 경우 로딩 방식을 조정할 수 있습니다. [web.dev 외부 자바스크립트 로딩 안내](https://web.dev/articles/efficiently-load-third-party-javascript)

운영자가 먼저 정할 것은 도구의 이름과 용도입니다. 광고를 중단한 도구인지, 실제로 확인하는 보고서가 있는지, 문의 완료 기록이 필요한지 담당자와 정리하세요. 로딩 시점을 늦추면 아주 짧게 방문하고 나가는 사용자의 측정에 영향을 줄 수 있어, 성능과 측정 범위를 함께 결정해야 합니다.

‘캐시 수명이 짧다’는 경고도 마찬가지입니다. 직접 제공하는 파일의 캐시 설정과 외부 업체가 제공하는 파일의 설정은 관리 주체가 다릅니다. 외부 파일의 캐시 기간을 우리 서버 설정만으로 바꿀 수 있다고 가정하지 말고, 그 기능의 필요성과 로딩 방식을 먼저 확인하세요. [MDN HTTP 캐싱 안내](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)

## 5. 스크롤 효과는 남기고, 반복 작업을 줄였습니다

화면을 움직일 때의 부담은 이미지 전송량과 별개였습니다. 브라우저는 요소의 크기와 위치를 계산하는데, 스크립트가 스타일을 바꾼 직후 크기를 반복해서 읽으면 강제 레이아웃 계산이 발생할 수 있습니다. [web.dev 레이아웃 반복 계산 안내](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing)

누비오 개선본에서는 일반적인 등장 효과를 화면에 가까워졌을 때 처리하고, 특정 스크롤 연출에 필요한 라이브러리도 해당 구간에 접근할 때 읽도록 조정했습니다. 커서 효과와 화면 크기 변경 처리에서도 불필요하게 반복되는 작업을 줄였습니다.

검수하다 보니 커서가 링크에서 벗어났는데도 커진 상태로 남거나, 낮은 창에서 시작해 높이를 늘리면 스크롤 효과가 켜지지 않는 문제도 발견했습니다. 이 부분까지 수정했습니다. 성능 작업은 기존 동작을 바꾸는 작업이기도 하므로, 파일이 작아졌다는 확인만으로 끝낼 수 없습니다. 이번 글에서는 강제 레이아웃 시간이 몇 밀리초 줄었다는 성과를 제시하지 않습니다.

## 6. 개선 완료는 같은 조건의 비교와 기능 검수로 확인합니다

개선 전후에는 같은 URL과 화면 조건으로 비교하고, 처음 방문하는 경우와 캐시가 남은 재방문을 구분하세요. 이번 이미지 검사는 390px·1200px·1440px 화면과 기기 픽셀 비율 1·2의 조합을 사용했습니다. 브라우저의 화면 모의 검수와 별도로 실제 휴대전화에서도 확인할 필요가 있습니다.

담당자와는 다음 항목을 완료 조건으로 합의하는 편이 좋습니다.

- 첫 화면의 이미지와 글이 빠짐없이 보이고, 작은 글자와 로고가 읽힙니다.
- 모바일 메뉴·페이지 이동·스크롤 효과가 기존 의도대로 작동합니다.
- 문의폼의 입력과 오류 안내, 접수 결과를 테스트 환경에서 확인합니다.
- 분석 이벤트가 필요한 시점에 남고 중복되거나 개인정보를 포함하지 않습니다.
- 배포 후 운영 URL에서 다시 측정하고, 확인한 조건과 남은 항목을 기록합니다.

첫 화면의 주요 이미지까지 일괄적으로 지연 로딩하는 방법은 피해야 합니다. LCP 이미지의 발견과 로딩을 늦추면 주요 콘텐츠 표시가 더 지연될 수 있습니다. 모든 자원을 최대한 늦추기보다 **먼저 보여야 하는 것과 나중에 필요한 것을 나누는 일**이 중요합니다. [web.dev LCP 최적화 안내](https://web.dev/articles/optimize-lcp)

또한 성능 개선이 검색 상위 노출을 보장하지는 않습니다. Google은 좋은 Core Web Vitals나 보고서 점수만으로 검색 순위가 보장되는 것은 아니라고 설명합니다. [Google 페이지 경험 안내](https://developers.google.com/search/docs/appearance/page-experience)
