## 홈페이지 문의폼은 ‘입력 항목’과 ‘접수 결과’를 함께 설계해야 합니다

문의폼을 만들 때 먼저 정할 것은 버튼 색상이 아닙니다. **첫 상담에 꼭 필요한 정보가 무엇인지, 무엇을 확인한 뒤 접수 완료라고 안내할지**입니다. 항목은 짧아도 담당자가 회신할 수 있어야 하고, 화면에 성공 메시지가 보여도 실제 문의가 전달되지 않았다면 접수가 완료된 것이 아닙니다.

처음에는 이름·회신 수단·문의 내용을 중심으로 구성하고, 회사명·기존 홈페이지·예산처럼 상담을 돕는 정보는 목적에 따라 선택 항목으로 두는 방식을 검토하세요. 이어서 전송 중·완료·실패·결과 확인이 어려운 상황을 구분하면 제작사와의 검수 기준도 명확해집니다.

이 글은 일반적인 제작·견적 문의를 기준으로 한 설계 제안입니다. 예약 확정이나 결제처럼 별도의 처리 이력이 필요한 서비스는 접수 기준을 더 엄격하게 정해야 합니다. 필수 항목 수를 줄인다고 문의가 반드시 늘어나는 것은 아니므로, 운영 방식과 실제 입력 불편을 함께 확인해야 합니다.

## 1. 필수 항목은 ‘없으면 다음 행동을 할 수 없는 정보’로 정하세요

## 2. 모바일에서는 무엇을 입력하는지 계속 보여야 합니다

입력칸 안의 예시만 보고 작성하게 하면, 글자를 넣는 순간 어떤 항목이었는지 확인하기 어려울 수 있습니다. ‘이메일’, ‘문의 내용’ 같은 제목은 입력칸 바깥에도 유지하고, 필수·선택 여부를 함께 표시하세요. W3C는 입력 요소와 연결된 레이블을 제공하도록 설명합니다. [W3C 입력 레이블 안내](https://www.w3.org/WAI/tutorials/forms/labels/)

디자인 시안보다 실제 휴대전화에서 다음 동작을 확인하는 편이 정확합니다.

- 이메일·전화번호 입력에 맞는 키보드가 표시되는지 확인합니다.
- 키보드가 열린 상태에서도 현재 입력칸과 다음 항목으로 이동할 방법을 확인합니다.
- 서비스 선택과 동의 체크박스를 손가락으로 누르기 어렵지 않은지 봅니다.
- 예산을 아직 모르는 사람도 무리 없이 다음 단계로 갈 수 있도록 합니다.
- 문의 내용을 길게 쓴 뒤 오류가 나도 작성 내용이 남아 있는지 확인합니다.

화면 배치 전반의 점검이 필요하다면 [모바일 홈페이지 최적화 글](/columns/website-mobile-optimization)도 참고하세요. 양식은 페이지의 일부이므로 헤더나 하단 고정 버튼이 입력을 가리는지도 함께 확인해야 합니다.

## 3. ‘전송 실패’만 보여주지 말고 다음 행동을 알려주세요

오류 안내는 원인에 따라 달라야 합니다. 이메일 형식이 잘못된 상황과 서버가 응답하지 않는 상황을 같은 문구로 처리하면 사용자는 무엇을 고쳐야 하는지 알 수 없습니다.

오류를 빨간색으로만 표시하지 말고 내용과 수정 방법을 글로 안내하세요. 화면낭독기에서도 오류와 완료 상태를 인지할 수 있도록 구현하는 것이 필요합니다. [W3C 폼 알림 안내](https://www.w3.org/WAI/tutorials/forms/notifications/)

## 4. 접수 완료 기준은 DB·메일·알림의 역할에 맞춰 정하세요

‘DB 저장’과 ‘메일 발송’은 서로 다른 처리입니다. **어느 쪽이 원본 보관 경로이고, 어느 쪽이 담당자 알림인지**를 먼저 합의해야 합니다. 둘 다 무조건 성공해야 하는지, 원본 보관이 완료되면 알림만 재시도해도 되는지는 업무에 따라 달라집니다.

일반적인 상담 요청이라면 다음 두 구성을 비교할 수 있습니다.

- **DB가 원본인 구성:** 저장 성공을 확인한 뒤 접수를 안내합니다. 담당자 메일 발송이 실패하면 원본을 보존한 상태에서 알림을 재처리합니다.
- **메일함이 원본인 구성:** 발송 결과뿐 아니라 운영 메일함 수신, 스팸 분류, 담당자의 확인 경로를 검수합니다. 메일함 용량과 계정 접근도 관리 대상입니다.

메일 서버가 요청을 수락한 것과 담당자가 메일을 읽은 것은 같은 상태가 아닙니다. 별도의 휴대폰 푸시 역시 확인을 돕는 알림으로 구분하고, 푸시 실패 때문에 이미 보관된 문의를 삭제하거나 전체 접수 실패로 바꾸지 않도록 설계하세요.

개발 검수에서는 ‘요청이 끝났다’만 확인하지 않도록 요청하세요. 예를 들어 브라우저의 `fetch()`는 서버가 오류 상태를 반환해도 항상 예외로 처리되는 것이 아니므로, 응답 상태와 서비스가 정한 접수 결과를 확인해야 합니다. [MDN Fetch 설명](https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch)

## 5. 비용을 비교할 때는 양식보다 운영 범위를 확인하세요

입력칸이 같아 보여도 문의폼 제작 범위는 다를 수 있습니다. 단순 이메일 전달과 관리자 목록, 첨부 파일, 담당자 배정, 재발송 기능을 포함한 구성은 필요한 작업이 다릅니다. 일률적인 가격 대신 아래 항목을 견적서에 구분해 달라고 요청하세요.

- 문의 원본의 보관 위치와 조회 방법
- 담당자 메일·휴대폰 알림의 연결 범위
- 파일 업로드의 종류·용량 제한과 보관 방식
- 스팸 요청 방어, 전송 횟수 제한, 중복 접수 대응
- 외부 메일·저장 서비스 이용료와 계정 소유자
- 장애 발생 시 확인할 기록과 유지보수 담당 범위

브라우저에서 검사하는 것만으로 끝내지 않고 서버에서도 입력을 검증해야 합니다. 입력 형식과 허용 범위를 어디서 확인하는지도 검수 범위에 넣으세요. [W3C 입력 검증 안내](https://www.w3.org/WAI/tutorials/forms/validation/)

[기업 홈페이지 제작](/service/corporate)을 의뢰할 때 이 항목을 함께 전달하면 문의 이후의 운영까지 논의하기 좋습니다. [현대오토닉스 제작 사례](/work/hyundai-autonics)에서는 기업의 정보를 전달하는 디자인 구성을 살펴볼 수 있습니다. 해당 사례 링크는 문의 전환 수치나 특정 접수 기능의 성과를 입증하는 자료는 아닙니다.

## 6. 오픈 전에는 ‘작성 → 접수 → 담당자 확인’까지 검수하세요

테스트 전송은 운영 담당자와 시점·테스트 표기를 합의하고 진행하세요. 실제 고객 문의와 섞이거나 외부 알림이 반복 발송되지 않도록 구분하는 것도 검수의 일부입니다.

1. PC와 휴대전화에서 필수 항목만 채워 접수할 수 있는지 확인합니다.
2. 빈 항목·잘못된 이메일을 넣었을 때 수정 방법이 안내되는지 봅니다.
3. 전송 중 버튼을 여러 번 눌렀을 때 중복 요청을 어떻게 처리하는지 확인합니다.
4. 저장·메일 서비스의 실패 상황은 테스트 환경에서 재현하고 입력 내용이 유지되는지 봅니다.
5. 완료 화면의 안내와 담당자가 확인하는 원본 내용이 일치하는지 비교합니다.
6. 알림을 끄거나 놓쳐도 원본을 다시 찾을 수 있는지 확인합니다.
7. 운영 계정의 접근 권한, 서비스 만료·용량, 장애 알림 담당자를 인수인계합니다.

방문 수가 적은 문제와 접수가 실패하는 문제는 분리해서 살펴야 합니다. 검색 유입이 없다면 [홈페이지가 검색되지 않는 원인](/columns/website-search-issues)을, 리뉴얼 이후 기능이 달라졌다면 [오픈 전후 리뉴얼 점검표](/columns/website-renewal-seo-checklist)를 함께 확인하세요.

## 문의폼을 바꾸려면 현재의 실패 상황부터 정리하세요

‘문의가 적다’보다 ‘휴대전화에서 예산 선택이 어렵다’, ‘메일은 도착했는데 실패로 표시된다’처럼 구체적인 현상을 적어 두면 개선 범위를 결정하기 쉽습니다. 사용 중인 페이지 주소, 원본 보관 경로, 담당자가 확인하는 방식, 재현 가능한 오류를 정리해 보세요. 비밀번호나 실제 고객 개인정보는 전달 자료에서 제외하세요.

기존 홈페이지의 입력 흐름과 접수 결과를 함께 개선하고 싶다면 [홈페이지 리뉴얼 서비스](/service/renewal)를 확인하거나 [프로젝트 문의](/contact)에 현재 불편한 상황을 남겨주세요. 필요한 기능과 운영 범위를 기준으로 검토할 수 있습니다.
