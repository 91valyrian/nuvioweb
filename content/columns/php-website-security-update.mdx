## 홈페이지가 잘 열리는데 PHP를 바꿔야 하나요?

**PHP 기반 홈페이지라면 화면이 정상으로 보이는 것과 보안 업데이트를 계속 받을 수 있는지는 따로 확인해야 합니다.** PHP는 서버에서 홈페이지의 코드를 실행하는 환경입니다. 방문자가 보는 디자인이 그대로여도 관리자 로그인, 게시판, 문의 접수 같은 기능을 실행하는 기반은 오래됐을 수 있습니다.

호스팅에서 “PHP 버전을 올려야 한다”는 안내를 받았는데, 바꾸면 기능이 멈출까 봐 미루고 있다면 먼저 두 가지를 나눠보세요. **지원이 끝난 환경을 계속 사용하는 문제**와 **기존 코드가 새 환경에 맞지 않는 문제**입니다. 전자는 보안 패치를 받을 경로를, 후자는 기능을 검증하고 수정할 범위를 확인해야 합니다.

누비오는 홈페이지 제작사의 관점에서 PHP 7과 8의 차이를 운영자가 판단할 수 있는 항목으로 정리하겠습니다. 이 글은 PHP를 사용하는 홈페이지가 대상입니다. 사용 기술을 모른다면 제작사나 호스팅사에 먼저 확인하세요. 모든 홈페이지가 PHP로 동작하는 것은 아닙니다.

## 1. PHP 7은 지원이 끝났고, PHP 8도 버전마다 다릅니다

PHP의 공식 지원에는 일반적인 버그와 보안 문제를 고치는 기간, 중요한 보안 문제에 한해 패치를 제공하는 기간이 있습니다. 이 기간이 끝나면 해당 계열은 PHP 프로젝트의 공식 지원 대상에서 제외됩니다. PHP 7의 마지막 계열인 **7.4는 2022년 11월 28일** 지원이 끝났습니다. 따라서 “PHP 7 중 가장 마지막 버전”이라는 설명만으로 현재 지원되는 환경이라고 볼 수 없습니다. [PHP 공식 지원 종료 목록](https://www.php.net/eol.php)

“PHP 8로 올렸다”는 설명도 충분하지 않습니다. 8.0과 8.1은 이미 지원이 종료됐고, 나머지도 기한이 서로 다릅니다. 아래는 **2026년 11월 20일 기준 PHP 프로젝트의 공식 지원 일정**입니다. 호스팅 업체가 제공하는 별도 유지지원 계약과는 구분해서 읽어주세요.

지원 상태와 일정은 [PHP 공식 지원 현황](https://www.php.net/supported-versions.php)에서 다시 확인할 수 있습니다. 전환할 때는 남은 지원 기간뿐 아니라 홈페이지의 CMS, 플러그인, 직접 개발한 기능과 호스팅이 해당 버전을 지원하는지도 함께 확인합니다. 가장 큰 숫자를 바로 선택하기보다 **계속 패치를 받을 수 있고, 사용 기능의 호환성을 검증할 수 있는 환경**을 정하는 것이 중요합니다.

같은 8.3 계열 안에서도 세 번째 숫자가 다른 패치 버전이 있습니다. 계열이 지원 중이라는 사실과 최신 보안 수정이 실제 서버에 적용됐다는 사실은 별개이므로, 정확한 버전과 패치 적용일을 확인하세요.

또한 일부 운영체제 공급사는 이전 버전 표기를 유지하면서 보안 수정만 가져오는 ‘백포트’를 제공합니다. [Red Hat의 보안 백포트 설명](https://access.redhat.com/security/updates/backporting)처럼 이런 지원을 받는 환경은 화면에 표시된 숫자만으로 취약 여부를 단정할 수 없습니다. 호스팅사에 공급 패키지, 지원 계약의 기한, 적용된 보안 공지를 확인해야 합니다. “호스팅이 되니 괜찮다”는 답변만으로는 패치 여부를 확인하기 어렵습니다.

## 2. PHP 7에서 8로 바꿨더니 오류가 나는 이유

새 버전에서는 이전에 허용되던 코드가 더 이상 실행되지 않거나, 같은 코드의 처리 결과가 달라질 수 있습니다. 예를 들어 PHP 8.0에서는 `each()`와 `create_function()`이 제거됐고, `count()`에 적절하지 않은 값을 전달하면 `TypeError`가 발생합니다. 숫자와 문자열을 느슨하게 비교하는 동작도 바뀌었습니다. [PHP 8.0 호환성 변경 안내](https://www.php.net/manual/en/migration80.incompatible.php)

홈페이지 운영자는 함수 이름을 모두 외울 필요는 없습니다. 다만 **서버의 버전 선택만 바꿔도 기존 프로그램이 자동으로 새 기준에 맞춰지는 것은 아니라는 점**은 알아두면 좋습니다. 오래된 게시판이나 플러그인, 회사에 맞춰 수정한 관리자 기능에 영향이 있을 수 있습니다.

## 3. 문제가 생기기 전에 취약점 업데이트를 해야 하는 이유

보안 패치는 알려진 결함을 수정하기 위한 작업입니다. 취약점의 영향은 서버 구성과 사용 기능에 따라 달라지지만, 해당되는 결함을 남겨두면 정보 노출이나 서비스 장애 등으로 이어질 가능성을 관리해야 합니다. **메인 화면이 열린다는 사실만으로 이런 문제가 없다고 확인할 수는 없습니다.** PHP 공식 보안 안내도 최신 변경 사항을 살피며 업데이트할 것을 권합니다. [PHP 보안 유지 안내](https://www.php.net/manual/en/security.current.php)

PHP 8 역시 보안 수정이 계속 나옵니다. [공식 변경 기록](https://www.php.net/ChangeLog-8.php)에는 보안 취약점을 식별하는 CVE 번호와 수정 내용이 기록돼 있습니다. 따라서 PHP 7에서 8로 한 번 옮겼다고 보안 관리가 끝나는 것은 아닙니다. 지원되는 계열 안에서 후속 패치를 적용하는 일도 유지관리 범위에 포함해야 합니다.

홈페이지에서는 PHP 외의 구성 요소도 살펴야 합니다. 워드프레스처럼 CMS와 플러그인·테마를 사용하는 사이트라면 각각의 업데이트와 호환성을 확인합니다. PHP만 갱신했다고 다른 구성 요소의 결함까지 수정되는 것은 아닙니다. [워드프레스 공식 보안 운영 안내](https://developer.wordpress.org/advanced-administration/security/hardening/)도 소프트웨어 업데이트와 백업 등을 함께 다룹니다.

그렇다고 버전이 오래됐다는 이유만으로 해당 홈페이지가 이미 침해됐다고 단정해서는 안 됩니다. 반대로 확인된 피해가 없다는 이유로 지원 종료를 무시할 수도 없습니다. 담당자가 할 일은 막연한 불안보다 **무엇이 설치돼 있고, 어떤 수정이 필요하며, 언제 반영할지**를 확인하는 것입니다.

## 4. 안전한 업데이트는 백업·테스트·운영 반영을 함께 준비합니다

업데이트를 의뢰할 때 “PHP를 올려주세요”만 전달하면 코드 수정과 기능 확인이 빠질 수 있습니다. 아래 순서를 작업 범위로 확인해 보세요.

1. **현재 환경을 기록합니다.** 웹사이트에 실제 적용된 PHP 버전, CMS·플러그인, 서버 설정과 필요한 확장 모듈을 확인합니다. 터미널의 PHP와 웹서버가 쓰는 PHP가 다를 수 있으므로 담당자에게 웹 실행 환경 기준으로 확인해 달라고 요청하세요.
2. **파일과 데이터베이스를 함께 백업합니다.** 첨부 파일, 설정, 복구에 필요한 접근 권한까지 확인합니다. 백업 파일이 있다는 보고에 그치지 말고 별도 환경에서 복구할 수 있는지도 검증합니다.
3. **분리한 테스트 환경에서 전환합니다.** 외부 메일·문자·결제 연동은 테스트 설정으로 바꾸거나 발송을 차단합니다. 운영 데이터를 사용해야 한다면 접근 범위를 제한하고 필요한 정보만 사용합니다.
4. **핵심 동작과 오류 기록을 확인합니다.** 메인 화면뿐 아니라 관리자·게시판·문의·파일·예약 작업을 점검하고 발견한 호환성 문제를 수정합니다. 오류를 숨긴 것만으로 해결됐다고 판단하지 않습니다.
5. **운영 반영과 되돌릴 기준을 정합니다.** 작업 시간, 중단 가능 범위, 확인 담당자, 어떤 오류가 나면 복구할지 미리 합의합니다. 반영 후 실제 버전과 기능·오류 기록을 다시 확인합니다.

특히 CMS 업데이트가 데이터베이스 구조까지 바꾸는 경우에는 PHP 설정만 되돌려도 복구되지 않을 수 있습니다. 파일과 데이터베이스의 복구 시점을 맞추고, 작업 도중 접수된 문의나 새 게시물이 있다면 어떻게 보존·대조할지 정해야 합니다. 이전 PHP로 돌아가는 조치는 장애 복구 수단이지, 지원 종료 환경을 계속 쓰기 위한 해결책은 아닙니다.

문의 기능의 점검 범위는 [문의폼 접수 오류 체크리스트](/columns/website-inquiry-form-checklist)에서 더 확인할 수 있습니다. 실제 운영 사이트에 고객처럼 보이는 테스트 문의를 남기지 말고, 별도 테스트 환경과 수신처에서 검증하세요.

## 5. 호스팅 관리와 홈페이지 유지보수의 경계를 확인하세요

서버를 관리하는 업체와 홈페이지 코드를 수정하는 업체가 다르면 맡은 범위도 다를 수 있습니다. “서버는 업데이트했다”와 “우리 회사의 문의·관리자 기능까지 확인했다”는 별도의 완료 보고입니다. 계약에 따라 아래 항목의 담당자를 정해 두세요.

- PHP·운영체제 패치와 지원 종료 안내를 누가 확인하는지
- CMS·플러그인·직접 개발한 코드의 호환성을 누가 수정하는지
- 백업 보관과 복구 검증, 장애 시 연락을 누가 담당하는지
- 운영 반영 후 어떤 기능을 어디까지 확인하고 기록하는지

업데이트 비용은 버전 숫자만으로 정하기 어렵습니다. 기존 프로그램의 관리 상태, 사용 중인 확장 기능, 직접 수정한 코드, 테스트할 연동과 데이터 규모에 따라 작업 범위가 달라집니다. 서버 환경 변경과 코드 수정, 기능 검수, 복구 준비를 구분해 견적을 확인하세요. 유지보수 계약을 새로 정한다면 [홈페이지 제작 계약의 유지보수·인수인계 항목](/columns/wrong-choice-agency)도 함께 살펴볼 수 있습니다.

## 6. 버전 전환으로 충분한지, 리뉴얼이 필요한지 판단하는 방법

PHP 지원이 끝났다고 디자인까지 모두 새로 만들어야 하는 것은 아닙니다. 현재 구조와 기능이 업무에 맞고 CMS·소스코드를 계속 관리할 수 있다면 환경 전환과 호환성 수정으로 진행할 수 있습니다. 반면 관리가 중단된 프로그램에 의존하거나 소스·접근 권한이 없고, 필요한 기능을 추가하기도 어렵다면 이전 또는 재구축 범위를 검토해야 합니다.

누비오에 [홈페이지 리뉴얼](/service/renewal)을 문의할 때는 **현재 주소, 호스팅사의 PHP 안내, 사용 중인 CMS, 오류가 나는 기능, 유지할 콘텐츠와 URL**을 전달해 주세요. 비밀번호나 고객 개인정보는 상담 자료에 넣지 않아도 됩니다. 이 자료를 바탕으로 기존 구조를 유지하며 보완할 범위와 새로 설계할 범위를 논의할 수 있습니다.

메뉴·콘텐츠·URL까지 바꾼다면 기술 환경 변경 외에 이전 작업도 필요합니다. [홈페이지 리뉴얼 URL 이전 체크리스트](/columns/website-renewal-seo-checklist)를 기준으로 기존 주소와 자료가 끊기지 않도록 범위를 정하세요.

**“PHP가 오래됐다는데 무엇부터 해야 할지 모르겠다”면 현재 환경을 확인하는 것부터 시작하면 됩니다.** [누비오 홈페이지 제작·리뉴얼 상담](/contact)에 호스팅 안내와 필요한 기능을 알려주세요. 단순한 버전 변경 요청을 넘어, 회사 홈페이지를 계속 운영하기 위해 필요한 수정·검수·이전 범위를 함께 정리하겠습니다.
