## 클로드 코드로 회사 홈페이지를 직접 만들 수 있나요?

**가능합니다. 다만 첫 화면을 만드는 것부터 문의 접수와 운영까지, 어디를 완성 기준으로 삼을지 먼저 정해야 합니다.** Claude Code는 프로젝트의 코드를 읽고 파일을 수정하며 명령을 실행하는 AI 코딩 도구입니다. 텍스트로 요구사항을 전달해 웹페이지 구현과 오류 수정을 도울 수 있습니다. 기능과 이용 환경은 [Anthropic의 Claude Code 공식 소개](https://code.claude.com/docs/en/overview)에서 확인할 수 있습니다.

소개 페이지나 작은 캠페인 랜딩처럼 범위가 명확한 작업부터 시작하면 제작 과정을 직접 살펴보기 좋습니다. 반면 회원 권한, 결제, 복잡한 예약, 기존 고객 데이터 이전이 필요한 사이트라면 화면 외의 검토 범위가 커집니다. AI가 코드를 만들었다는 사실만으로 운영 준비가 끝나는 것은 아닙니다.

이 글은 **클로드 코드로 홈페이지를 만들고 싶은 대표·마케팅 담당자**를 위한 제작 가이드입니다. 설치 명령이나 특정 모델의 성능 비교보다, 어떤 자료를 준비하고 어떤 순서로 요청하며 무엇을 검수할지에 집중합니다. 일반 AI 제작 도구의 특징은 [AI 홈페이지 제작을 검토할 때 알아둘 점](/columns/ai-homepage-limit)과 함께 읽어보세요.

## 1. “예쁘게 만들어줘”보다 먼저 준비할 다섯 가지

AI에게 디자인을 요청하기 전에 짧은 프로젝트 메모를 만들어보세요. 복잡한 기획서가 아니어도 됩니다. 아래 항목을 한 장에 정리하는 것부터 시작할 수 있습니다.

  <thead><tr><th>준비 자료</th><th>구체적으로 정할 내용</th></tr></thead>

    <tr><td>페이지와 콘텐츠</td><td>회사 소개, 서비스, 사례, 문의 등 필요한 메뉴와 실제 원고</td></tr>

실제 사례나 고객 후기가 없다면 그 자리를 임의의 실적으로 채우지 마세요. 인증, 거래처 로고, 성과 수치도 확인된 자료만 사용합니다. 화면에 들어갈 문구를 AI가 제안하더라도 사실 여부는 담당자가 확인해야 합니다.

참고 사이트는 전체 복제를 요청하기보다 “큰 제목과 넉넉한 여백”, “서비스별로 구분된 메뉴”처럼 **좋아하는 요소를 설명하는 기준**으로 사용하세요. 처음 준비할 항목이 막막하다면 [홈페이지 제작 전 준비할 내용](/columns/website-without-prep-loses-direction)을 먼저 정리해도 좋습니다.

처음부터 전체 사이트를 한 번에 요청하면 무엇을 확인해야 할지 놓치기 쉽습니다. 메인 화면을 기준으로 디자인 방향을 정하고, 공통 요소를 확정한 뒤 상세 페이지와 기능으로 확장하는 순서를 권합니다.

### 먼저 현재 상태와 변경 계획을 확인합니다

기존 프로젝트가 있다면 사용 중인 프레임워크, 페이지 구조, 실행 방법, 기존 디자인 규칙부터 확인하도록 요청하세요. 새 프로젝트라면 콘텐츠를 직접 수정할지, 어떤 환경에서 운영할지부터 정합니다. 개발 방식의 이름을 많이 나열하는 것보다 운영 담당자가 할 일을 설명하는 편이 요구사항 정리에 도움이 됩니다.

다음은 **가상의 B2B 서비스 소개 사이트를 위한 요청 예시**입니다. 누비오의 실제 납품 사례나 특정 결과를 보장하는 프롬프트가 아닙니다.

> 기업 담당자가 서비스 내용을 이해하고 상담을 요청할 수 있는 홈페이지를 만들려고 합니다. 필요한 페이지는 메인, 서비스 소개, 제작 사례, 문의입니다. 먼저 제공한 원고와 현재 프로젝트를 확인하고 페이지별 구성과 구현 순서를 정리해 주세요. 자료에 없는 실적·고객 로고·후기는 만들지 말고 필요한 자료로 표시해 주세요. 디자인은 메인 화면부터 제안하고 모바일 구성도 함께 확인해 주세요.

Anthropic의 [Claude Code 활용 지침](https://code.claude.com/docs/en/best-practices)은 코드만으로 알 수 없는 맥락을 제공하고, 결과를 확인할 수 있는 검사 기준을 주는 것을 강조합니다. “모바일도 확인해줘” 대신 확인할 화면과 동작을 구체화하는 식으로 적용할 수 있습니다.

### 화면 단위로 구현하고 기준을 남깁니다

메인 화면을 확인한 뒤 색상, 제목 크기, 콘텐츠 폭, 버튼, 카드 형태를 공통 기준으로 정하세요. 이후에는 그 기준을 사용해 상세 페이지와 문의 화면을 확장하도록 요청합니다. 수정할 때도 “전체적으로 더 좋게”보다 “서비스 카드의 제목은 이미지 하단에 겹치고 밝은 이미지에서도 읽히게”처럼 대상과 원하는 상태를 지정하세요.

프로젝트의 지속적인 규칙은 `CLAUDE.md`에 정리할 수 있습니다. 예를 들어 사용해야 할 실행·검사 명령, 콘텐츠 파일 위치, 기존 URL 보존 원칙을 남기는 방식입니다. 다만 문서에 적어두는 것만으로 준수가 보장되지는 않으므로 실제 변경 내용과 검사 결과를 함께 확인해야 합니다. [공식 활용 지침의 프로젝트 맥락·검사 기준 설명](https://code.claude.com/docs/en/best-practices)을 참고하세요.

### 완료 보고에는 확인한 결과를 요구합니다

구현 후에는 변경한 파일, 실행한 검사, 확인한 화면, 아직 연결하지 못한 기능을 구분해 보고하도록 요청하세요. “빌드 성공”과 “브라우저에서 버튼이 작동함”은 별개의 확인입니다. 화면을 직접 확인하지 못했다면 그 사실도 남겨야 합니다.

> 방금 만든 페이지를 실제 로컬 서버에서 확인해 주세요. PC와 모바일에서 가로 넘침, 제목 줄바꿈, 메뉴와 버튼 이동을 점검하고 오류를 수정해 주세요. 프로젝트에 정의된 빌드와 관련 검사를 실행해 결과를 알려주세요. 문의는 별도의 테스트 환경과 테스트 수신처에서 저장·수신까지 확인하고, 운영 배포는 별도 승인 전 진행하지 마세요. 확인하지 못한 항목은 완료로 표시하지 말아 주세요.

## 3. 직접 만들 범위와 전문가가 확인할 범위를 나누세요

아래는 제작 방식을 고르기 위한 판단 기준입니다. Claude Code가 특정 기능을 만들 수 없다는 뜻이 아니라, **잘못되었을 때 확인하고 복구할 수 있는지**를 기준으로 범위를 나누는 방법입니다.

<table>
  <thead><tr><th>사이트의 상황</th><th>추천하는 진행 방식</th></tr></thead>
  <tbody>
    <tr><td>제품 소개 초안·내부 시안</td><td>직접 구현하며 원고와 디자인 방향을 검토</td></tr>
    <tr><td>공개할 소규모 소개·랜딩페이지</td><td>직접 제작 후 모바일·문의·배포 설정을 검수할 담당자 확보</td></tr>
    <tr><td>담당자가 자주 수정하는 기업 사이트</td><td>CMS와 권한, 수정 이력, 백업·복구 방법까지 함께 설계</td></tr>
    <tr><td>회원·결제·민감한 정보·기존 데이터 이전</td><td>경험 있는 개발자가 구조와 연동, 접근 제어, 복구 계획을 검토</td></tr>
  </tbody>
</table>

소스코드를 받는 것과 담당자가 사이트를 편하게 관리하는 것은 다릅니다. 공지 하나를 바꿀 때마다 코드 수정과 배포가 필요하다면, 그 운영 방식을 감당할 수 있는지 확인해야 합니다. 회사·제품·문의 구조를 함께 설계해야 한다면 [기업 홈페이지 제작](/service/corporate), 한 가지 제안과 신청 흐름에 집중한다면 [랜딩페이지 제작](/service/landing-page)의 구성도 비교해 보세요.

실제 기업 사이트의 정보 구성은 [현대오토닉스 제작 사례](/work/hyundai-autonics)에서 살펴볼 수 있습니다. 이 링크는 서비스·제품 정보를 전달하는 디자인 참고이며, Claude Code로 제작했다는 사례나 AI 제작 성과를 뜻하지 않습니다.

## 4. 비용은 AI 사용료 외의 운영 항목까지 계산하세요

AI 사용료만 비교하면 제작비를 작게 보기 쉽습니다. 프로젝트에 따라 도메인, 호스팅, 메일 발송, 데이터 저장, 유료 이미지·폰트, 관리자 기능과 유지관리 비용이 추가될 수 있습니다. 사용 서비스의 요금과 무료 제공 범위는 계약 시점의 공식 안내를 확인하세요.

직접 제작에서는 담당자의 작업 시간도 비용입니다. 오류를 찾는 시간, 원고를 정리하는 시간, 배포 문제를 해결하는 시간을 함께 고려해야 합니다. 전문가에게 일부 검수만 맡긴다면 “AI로 만들었으니 수정만”보다 저장소, 실행 방법, 구현된 기능과 남은 문제를 전달해야 범위를 판단하기 쉽습니다. [홈페이지 제작 비용 가이드](/columns/homepage-cost-guide)에서 견적 항목을 나눠 확인해 보세요.

또한 코드·도메인·호스팅·저장소 계정의 소유자를 기록하고, 실제 운영자가 로그인과 복구를 할 수 있는지 확인하세요. 개인 계정 한 곳에 모든 권한이 모이면 담당자가 바뀔 때 인수인계가 어려워질 수 있습니다.

### 모바일과 사용성

휴대전화에서 메뉴를 열고, 서비스 설명을 읽고, 문의 화면으로 이동해 보세요. 제목이 잘리거나 버튼이 화면 밖으로 밀리지 않는지, 가로 스크롤을 의도하지 않은 곳에서 발생하지 않는지 확인합니다. 키보드로 링크와 입력칸을 이동할 때 현재 위치가 보이는지도 점검하세요.

### 문의와 데이터 처리

문의 버튼을 눌렀을 때 성공 메시지만 보이는지, 실제 저장과 담당자 수신까지 이루어지는지 구분해야 합니다. 테스트 환경에서 정상 제출, 필수 정보 누락, 저장·메일 장애 상황의 처리를 확인하세요. 운영 사이트에 실제 고객처럼 보이는 테스트 문의를 남기는 방식은 피하고 테스트 수신처와 데이터를 따로 사용하세요.

서버에서만 사용해야 할 API 키가 브라우저 코드에 포함되지 않는지도 확인합니다. AI에 맡길 수 있는 작업 범위와 접근 권한은 프로젝트별로 정해야 합니다. 구체적인 설정 방식은 [Claude Code 권한 문서](https://code.claude.com/docs/en/permissions)를 참고하세요. 글로 “조심해 달라”고 요청하는 것과 도구의 접근 범위를 설정하는 것은 별개의 작업입니다.

### 검색과 공개 설정

페이지 제목과 설명이 실제 내용을 나타내는지, 메뉴와 본문 링크가 올바른 주소로 연결되는지 확인하세요. 공개할 사이트에 개발용 검색 차단 설정이 남지 않았는지, 반대로 관리자·미공개 페이지가 공개 목록에 포함되지 않았는지도 살펴봅니다.

검색 설정은 노출의 기본 조건을 점검하는 작업이지 순위를 보장하는 장치가 아닙니다. Google도 특정 사이트의 색인이나 최상위 순위를 보장하지 않는다고 안내합니다. [Google 검색엔진 최적화 기본 가이드](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)를 기준으로 확인하고, 기존 사이트를 바꾼다면 [리뉴얼 URL 이전 체크리스트](/columns/website-renewal-seo-checklist)도 함께 검토하세요.

## 6. 제작을 시작하기 전, 이 질문에 답할 수 있나요?

- 방문자가 해야 할 행동과 그 행동까지의 페이지 구성이 정해져 있나요?
- 실제로 사용할 원고·이미지와 확인된 소개 자료가 있나요?
- 문의가 어디에 저장되고 누구에게 도착하는지 알고 있나요?
- PC·모바일에서 직접 확인할 담당자가 있나요?
- 수정·배포·장애 복구를 누가 맡을지 정했나요?
- 소스코드와 도메인·호스팅 계정을 운영자가 관리할 수 있나요?

답하기 어려운 항목이 있다면 그 부분이 먼저 정리해야 할 제작 범위입니다. Claude Code를 활용하면 초안 구현과 반복 수정에 도움을 받을 수 있습니다. 그 결과를 회사가 실제로 사용할 웹사이트로 연결하려면 콘텐츠, 기능, 검수, 운영의 기준이 함께 필요합니다.

직접 만든 시안을 공개 가능한 홈페이지로 정리하고 싶다면 [누비오에 프로젝트를 상담해 보세요](/contact). 현재 화면이나 저장소, 필요한 기능, 원하는 운영 방식과 남은 문제를 알려주시면 구현·검수 범위를 함께 논의할 수 있습니다.
